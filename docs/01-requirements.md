# 01 需求分析

> 对应题目：小影校招第 4 题“短视频脚本 Agent”。题目原文见施工方案附录 A：`docs/superpowers/plans/2026-11-02-video-script-agent.md`（第 1754 行起）。

## 用户

短视频创作者，尤其是刚开始做口播或剪辑、还没有稳定素材库的人。他们没有专职编导，需要一条能在几分钟内改完就用的脚本，并且不希望脚本里出现自己产品或素材证不出来的说法。

次要用户是审核脚本的人（品牌方、运营）。他们需要能逐条追问“这句话出自哪条素材、这一版到底多长、检查过没有”。

## 目标

1. 把需求（主题、受众、平台、目标时长、风格）变成一份可编辑的脚本：标题、分镜、旁白/字幕、预计总时长、素材来源 ID、风险。
2. 脚本里的产品事实必须能逐条追溯到素材原文，不允许出现素材没有的功能、数字、效果。
3. 时长必须由工具估算并被检查，不能由模型口头声明。
4. 需求不完整、素材不足、工具不可用、目标时长做不到时，给出明确状态和原因，不猜、不编。

## 范围内

- CLI 入口，一条命令跑一次，产出 4 个文件：`result.json`、`script.md`、`trace.jsonl`、`trace.md`。
- 模型驱动的 ReAct 循环：模型选择动作 → 代码执行工具 → 结果回给模型 → 模型决定下一步，直到终止动作或达到上限。
- 三个业务工具：`search_materials`（素材检索）、`estimate_duration`（时长估算）、`check_rules`（品牌规则与来源检查）。
- 三个终止动作：`submit_script`（需通过把关）、`ask_user`、`report_failure`。
- 合成素材与品牌规则（`data/`），以及一个改变素材的变体（`examples/data_variants/no_subtitle/`），用来验证“检索结果变了动作会不会变”。
- 离线 Mock 入口，用于没有密钥时验证流程。
- 10 个真实模型用例及其运行记录（`examples/real/`），一致性测试核对已提交的记录。

## 范围外

- **不生成视频**：不渲染画面、不合成配音、不出 MP4。产出的“分镜画面”只是文字描述。
- **不做界面**：没有 Web UI、桌面端或移动端。题目允许 CLI/HTTP API/Notebook 三选一，这里选 CLI。
- **不做部署**：没有 Docker、Serverless、CI 配置，也没有生产级 Runtime、队列、并发或持久化。
- **不接真实发布**：不调用任何平台的发布接口，不上传素材，不做账号授权。
- **不做真实素材接入**：素材是 6 条合成数据（P01–P06），没有向量检索或线上素材库；检索是词项匹配。
- **不做多 Agent**：单进程、单循环，模型是唯一决策者。

## 成功标准

对应题目“必须验收”的 5 个点，每个点都有已提交的真实运行记录（详见 `docs/03-evaluation.md`）：

| 验收点 | 成功标准 | 对照用例 |
|---|---|---|
| 正常生成 | 产出标题、分镜、旁白、总时长、来源 ID、风险，状态 `completed`，时长和规则检查都 `pass` | `01_normal` |
| 缺关键信息 | 主题或目标时长缺失时不猜，调 `ask_user`，状态 `needs_input`，`missing_info` 写明缺什么 | `02_missing_target` |
| 无素材 | 检索无结果时先改写查询，仍无结果就请求补充素材，状态 `needs_input` | `03_no_material` |
| 工具失败 | 工具不可用时按 `retries_left` 决定重试或结束；失败绝不算检查通过 | `04_tool_fail_transient`（恢复）、`05_tool_fail_permanent`（明确失败） |
| 超时长后的修正或明确失败 | 能压缩就压缩后重新检查并 `completed`；做不到就 `report_failure` 并说明差距 | `06_over_duration_fixed`（修正）、`07_over_duration_infeasible`（明确失败） |

对应“审核要点”：

1. **素材 ID、分镜时长、检查结果逐一对应。** `result.json` 的每个分镜带 `source_ids` 和 `duration_sec`，`checks` 记录最后一次判定；`tests/test_examples_consistency.py` 的 `test_completed_results_recompute_exactly` 会用同一份 `data/` 重算，逐镜核对时长、核对 `quote` 是素材原文、核对 `verdict == "pass"`。
2. **改变时长或检索结果，下一步动作是否调整。** `01`→`07` 只改目标时长（30 秒→3 秒）：`01` 走“检索×3 → 估算(pass) → 检查(fail) → 估算 → 检查(fail) → 估算 → 检查(pass) → 提交”，`07` 走“检索 → 估算(too_long) → 检查 → 估算 → 检查 → 估算 → 估算(仍 too_long) → `report_failure`”；`01`→`10` 只改素材目录，`10` 从“检索命中”变成“三次零结果→`ask_user`”。两组都在 `examples/real/` 里有记录。
3. **有效修正与事实可追溯。** `06` 首估 15.25 秒（目标 12 秒）判 `too_long`，压缩后 9.75 秒通过；`09` 首估 34.25 秒（目标 30 秒）判 `too_long`，压到 25.5 秒通过。所有 `completed` 用例的 `quote` 都能在 `data/materials.json` 里逐字找到。
4. **编造产品事实属于关键缺陷。** `08_rule_conflict` 的用户要求写“效率提升 80%”，素材没有这条数据；记录显示脚本没有写，改为在 `risks` 里说明。`cases.json` 对全部 10 个用例都设了 `forbid_text`（`80%`、`效率`、`效率提升`），一致性测试逐条检查最终脚本。规则还会拦下超出素材字面意思的效果和能力说法，比如“放哪都行”“帮你搞定”，但语义层面仍有限制，见 `docs/03-evaluation.md`。

## 题目未定义时的假设

| 问题 | 采用的做法 |
|---|---|
| 关键信息 | 主题和目标时长必填；受众、平台、风格缺失时按通用设定，写入 `risks` |
| 时长算法 | 汉字每秒 4 个，分镜间隔 0.5 秒，单镜不少于 2 秒 |
| 时长合格范围 | 目标时长的 80%–100% |
| 防编造 | 引用逐字校验、数字校验、效果和能力词表、标签引用校验 |
| 工具失败 | 模型最多重试一次，仍失败就 `report_failure` |
| 步数上限 | 10 轮模型决策，工具调用不超过 20 次 |
| 产品 | “剪刀鱼”是虚构产品，全部素材为合成数据 |

补充说明：

- 上表“工具失败最多重试一次”在代码里的落地方式是 `retries_left = max(0, 2 - 连续失败次数)`，模型看到 `0` 时被要求 `report_failure`。重试与否仍然由模型决定，代码只提供这个数字和提示。
- 时长算法与合格范围写在 `data/duration_config.json`：`chars_per_sec=4.0`、`pause_per_shot_sec=0.5`、`min_shot_sec=2.0`、`lower_ratio=0.8`。改这个文件即可改口径，不用改代码。
- 目标时长上限为 600 秒，`0`、负数、无法解析、超过上限都视为无效，交给模型追问。
- 同一份脚本的时长和规则都 `pass` 才能提交。判定按脚本内容哈希关联，检查后改稿必须重新检查。
