### 1. 数字校验把“1”当成“12”的依据

**问题。** 事实校验最初用“数字是素材事实的子串”判断数字有没有素材支持。于是引用 P04 的 `提供 12 种中文配音音色`、脚本写 `提供 1 种音色` 也能通过，因为 `1` 是 `12` 的子串；同理 `80` 会被 `1080` 放行。

**发现方式。** 代码审查第一轮指出：数字门用的是子串包含，`提供 1 种音色` 引用 P04 的 `提供 12 种中文配音音色`、`支持导出 80P` 引用 P03 的 `支持导出 1080P`，两者都得到零违规和 `pass`。随后先补回归测试 `tests/test_rules.py::test_shortened_quantity_is_rejected`，确认在旧实现上失败（RED：`assert 'UNSUPPORTED_NUMBER' in set()`），再改实现（GREEN）。

**修复。** `63e010b fix: require whole number tokens in fact matching`。新增 `_contains_number`，用 `(?<!\d)…(?!\d)` 要求数字是完整数字串。`1080` 仍然能匹配 `1080P`，`12` 匹配 `提供 12 种`，但 `1` 不再匹配 `12`。

### 2. 密钥可能进入 Trace（三轮修复）

**问题。** Trace 要求“密钥不进记录”，但初版只对部分字段做了处理，自由文本摘要、错误信息、字段名三条路径都可能带出密钥。

**发现方式。** 第一轮代码审查把三条路径都列为必修：自由文本摘要、错误信息、字段名。修复过程中又逐路径复查，发现 `_clip` 先截断后替换，跨截断点的密钥会被切成残片（残片不再匹配 `sk-` 正则）；以及 `secrets` 传单个字符串时被逐字符迭代成“每个字符都是密钥”。

**修复（三个提交，一个比一个深）：**

- `468c06b fix: redact trace summaries, key names and configured secrets`：摘要、参数名、已配置密钥全部纳入脱敏。
- `8cdf412 fix: redact before clipping and normalize bare-string secrets`：改为先脱敏再截断；`secrets` 传单字符串时按一个密钥处理。
- `ee6bf3e fix: pass secrets into summary redaction and cover error paths`：把密钥列表传进摘要函数内部，并覆盖错误分支。

**后续。** `9000598 test: cover direct summary redaction paths` 整理测试。复查时发现其中一条新测试在修复前的提交上也能通过（没有区分力）：因为 `step()` 层还有一道外层脱敏，掩盖了 fallback 密钥的缺陷。保留了一条确实会失败的用例（裸字符串被逐字符替换，旧实现产生 5 个以上星号），另一条降级为直接调的回归覆盖。

### 3. 引用原文里的竖线撑破 Markdown 表格

**问题。** `script.md` 用 Markdown 表格列分镜，`claims` 的 `quote` 直接拼进单元格。素材原文里只要有一个 `|`，整行就会错位。

**发现方式。** Task 9 自检渲染逻辑时发现：表格单元格里的竖线没有转义，`quote` 或画面描述里含 `|` 就会多切出列。修复后逐行统计行内竖线数量固定为 9（6 列 + 边界）。

**修复。** `adfc6fc fix: escape table pipes in claim quotes`，在 `_claims_text` 里转义 `|`。

### 4. 故障计划写进 Trace 变成 `null`

**问题。** `FaultPlan` 是 dataclass，`TraceRecorder` 的 `fault` 参数按 `dict | None` 处理，直接传 dataclass 会被判为非 dict，`trace.jsonl` 首行写成 `"fault": null`，注入记录就丢了。

**发现方式。** 做对照实验：把 dataclass 直接传进去，读 `trace.jsonl` 首行，确认是 `null`。

**修复。** 在 `app.py` 加 `_fault_record`，先转成 `{"tool": ..., "times": ...}` 再交给 `TraceRecorder`。该修正随 `14c20b2 feat: add cli, markdown output and offline mock entry` 提交，并由 `tests/test_cli.py::test_fault_plan_is_serialized_into_trace` 固定。

### 8. Web 工作台实现中的问题

- **开发环境禁止本机回环连接。** `asyncio` 在 Windows 上建事件循环依赖回环 socket，所以 FastAPI、uvicorn 和 `TestClient` 一启动就卡死。发现方式：用 `faulthandler` 打印卡住时的调用栈，停在 `socket.socketpair` 的 `accept`。处理：后端改用标准库 `ThreadingHTTPServer`，路由集中到不依赖 socket 的 `dispatch()`。
- **记录列表显示成 `[object HTMLButtonElement]`。** `replaceChildren` 不会展开数组，单元测试看不出来，是浏览器实测抓到的。
- **`hidden` 属性不生效。** `.field`、`.actionbar` 的 `display: flex` 覆盖了浏览器默认的 `[hidden]` 样式，本该隐藏的区块还在显示。自查 CSS 时发现，加了全局规则，并补了浏览器检查。

## 最难问题

**最难的是判断“状态全绿”到底算不算做对了。** 前两批真实运行 10/10 达到预期状态，316 条测试全过，一致性测试逐镜检查时长和引用原文，看起来已经收工。但人工把 5 个 `completed` 的脚本逐句读下来，发现“字幕放哪都行”“它能帮你搞定”这类句子根本不在 P01 的“支持字幕”里——规则没拦，测试也测不出来。

难点不在改，在于意识到**测试只能证明“符合规则”，证明不了“规则够用”**。当时的测试断言的是 `check_rules` 返回 `pass`，而被测对象本身有洞，测试就跟着一起漏。解决办法是换一个判据：拿素材原文当唯一标准，逐句问“这句能对应到哪条 facts”。问下来 5 个脚本全不达标，于是收紧 Prompt、把词表从 24 个扩到 62 个、把问题句子写成回归测试，再全量重跑第三批。

第二个难的是**改了规则之后旧记录全部失效**。新词表下旧的 5 个 `completed` 样例全部不再通过，`test_completed_results_recompute_exactly` 直接失败。一开始的反应是“能不能只重跑失败的”，但那样 `examples/real/` 就成了两批不同规则的混合产物，一致性测试失去意义。最后决定 10 个用例全部重跑——多花一倍时间，但记录是同一套规则下的。

第三个是“**加素材库反而暴露了产品定位问题**”。为了让娱乐向选题能跑通，加了一套 8 条素材的娱乐库，结果发现“纯剧情、零产品植入”的脚本被 `NO_SOURCE` 规则硬拦，永远无法 `completed`。题目只要求产品事实可追溯，并没有要求必须植入产品——这是实现时自己加的约束，比题目更严。用户实际使用时要求“不带产品的搞笑短剧”，模型追问“是否接受不出现产品”，其实是在问一个代码不允许的选项。这个问题到交付时也没改，因为它牵涉产品定义，不是纯技术决定。

## 学习收获

- **“通过检查”和“是对的”是两件事。** 这套项目的价值在于把判据写死成代码和测试，但它同时说明：确定性规则只能覆盖你已经想到的说法。没想到的夸大，词表拦不住；而换一种说法就能绕过。真正要防编造，得有一个独立于生成方的审校环节，而不是让生成方自己过一遍词表。
- **让模型自己看工具结果，比把答案写进 Prompt 更能看出能力。** 系统提示里故意不写“每秒 4 字”和品牌语，模型必须真的读 `estimate_duration` 和 `check_rules` 的返回才知道怎么改。代价是多跑几轮，好处是 Trace 里能观察到“按违规清单改”这件事，而不是模型心算后一次写对。如果把口径全写进 Prompt，回合数会少，但也就测不出模型会不会用工具了。
- **哈希门禁这类“防作弊”设计，本质是把不变量写成机制。** `draft_hash` 只做一件事：提交的稿子必须是检查过的那一份。实现只用了十几行，但它让“先检查一份、再提交另一份”这条路彻底走不通，比在 Prompt 里反复叮嘱可靠得多。
- **文档里的每个数字都该能重算。** 写评估文档时最大的收获是养成“写结论前先跑一遍”的习惯——`summary.json` 的 token 合计、测试通过数、每批运行的时间戳，全部从产物里取，不凭印象写。后期加素材库导致一条断言过时，也是靠重跑才发现，只看文档发现不了。
- **限制要写清楚，而不是藏起来。** 九条已知限制每条都给了实测复现方法，包括“第一次会被‘第一’误拦”这种难看的误报。评审真正会问的是“你知道它错在哪吗”，而不是“它有没有错”。

## 下一步

按优先级：

1. **把 Web 工作台和这批代码提交。** 当前工作区有 71 个改动文件没进 git，其中 `src/script_agent/web/`（整个 Web 工作台）、`src/` 下 5 个文件的修改、`tests/test_web_*.py` 都处于未跟踪或未提交状态。README 和 `docs/04-ai-usage.md` 已经把 Web 工作台当成交付物在描述，但仓库里还没有对应的提交，这是最该先补的。
2. **决定“纯剧情”要不要支持。** 也就是 `NO_SOURCE` 这条规则是保留还是降级为风险提示。保留就是明确“本项目只做产品推广脚本”，写进 `docs/01-requirements.md` 的范围外；降级就把判定从 `check_rules` 里拿掉，改由结果里的 `risks` 如实标注“未引用任何产品素材”。我倾向降级——题目没有要求必须植入，而且现在这样的结局是模型被迫在剧情里硬插两句产品台词，反而更难读。
3. **素材库要扩。** 默认库 6 条素材、7 条事实，每条一到两句话，撑不起 30 秒有信息量的脚本。实测把所有事实全用上也只到 19.5 秒，模型只能靠重复同一句或情绪铺垫凑时长，而词表又会误拦“快速”“跟着”“不用”这类正常表达。真要用起来，一个卖点至少要有三到五条事实。
4. **补语义层面的校验。** 现在词表是子串匹配，换说法就漏。可行的方向是加一次独立的事实审校（另一次模型调用，或人工抽检），但要把“判定不可复现”和“成本翻倍”这两个代价算清楚再决定。
5. **把 Web 的真实 socket 端到端固化成常规验证。** 这条用例有 `skipif` 探针，环境不允许本机回环时会静默跳过，等于没有覆盖。本次在允许回环的环境里跑通了（`317 passed, 0 skipped`），但换一台机器可能又跳过。应该在 CI 或验收脚本里显式检查“这条用例是否真的执行过”，而不是只看 `0 failed`。
