### 1. 数字校验把“1”当成“12”的依据

**问题。** 事实校验最初用“数字是素材事实的子串”判断数字有没有素材支持。于是引用 P04 的 `提供 12 种中文配音音色`、脚本写 `提供 1 种音色` 也能通过，因为 `1` 是 `12` 的子串；同理 `80` 会被 `1080` 放行。

**发现方式。** 代码审查第一轮指出：数字门用的是子串包含，`提供 1 种音色` 引用 P04 的 `提供 12 种中文配音音色`、`支持导出 80P` 引用 P03 的 `支持导出 1080P`，两者都得到零违规和 `pass`。随后先补回归测试 `tests/test_rules.py::test_shortened_quantity_is_rejected`，确认在旧实现上失败（RED：`assert 'UNSUPPORTED_NUMBER' in set()`），再改实现（GREEN）。

**修复。** `63e010b fix: require whole number tokens in fact matching`。新增 `_contains_number`，用 `(?<!\d)…(?!\d)` 要求数字是完整数字串。`1080` 仍然能匹配 `1080P`，`12` 匹配 `提供 12 种`，但 `1` 不再匹配 `12`。

### 2. 密钥可能进入 Trace（三轮修复）

**问题。** Trace 要求“密钥不进记录”，但初版只对部分字段做了处理，自由文本摘要、错误信息、字段名三条路径都可能带出密钥。

**发现方式。** 第一轮代码审查把三条路径都列为必修：自由文本摘要、错误信息、字段名。修复过程中又逐路径复查，发现 `_clip` 先截断后替换，跨截断点的密钥会被切成残片（残片不再匹配 `sk-` 正则）；以及 `secrets` 传单个字符串时被逐字符迭代成“每个字符都是密钥”。

**修复（三个提交，一个比一个深）：**

- `468c06b fix: redact trace summaries, key names and configured secrets`：摘要、参数名、已配置密钥全部纳入脱敏。
- `8cdf412 fix: redact before clipping and normalize bare-string secrets`：改为先脱敏再截断；`secrets` 传单字符串时按一个密钥处理。
- `ee6bf3e fix: pass secrets into summary redaction and cover error paths`：把密钥列表传进摘要函数内部，并覆盖错误分支。

**后续。** `9000598 test: cover direct summary redaction paths` 整理测试。复查时发现其中一条新测试在修复前的提交上也能通过（没有区分力）：因为 `step()` 层还有一道外层脱敏，掩盖了 fallback 密钥的缺陷。保留了一条确实会失败的用例（裸字符串被逐字符替换，旧实现产生 5 个以上星号），另一条降级为直接调的回归覆盖。

### 3. 引用原文里的竖线撑破 Markdown 表格

**问题。** `script.md` 用 Markdown 表格列分镜，`claims` 的 `quote` 直接拼进单元格。素材原文里只要有一个 `|`，整行就会错位。

**发现方式。** Task 9 自检渲染逻辑时发现：表格单元格里的竖线没有转义，`quote` 或画面描述里含 `|` 就会多切出列。修复后逐行统计行内竖线数量固定为 9（6 列 + 边界）。

**修复。** `adfc6fc fix: escape table pipes in claim quotes`，在 `_claims_text` 里转义 `|`。

### 4. 故障计划写进 Trace 变成 `null`

**问题。** `FaultPlan` 是 dataclass，`TraceRecorder` 的 `fault` 参数按 `dict | None` 处理，直接传 dataclass 会被判为非 dict，`trace.jsonl` 首行写成 `"fault": null`，注入记录就丢了。

**发现方式。** 做对照实验：把 dataclass 直接传进去，读 `trace.jsonl` 首行，确认是 `null`。

**修复。** 在 `app.py` 加 `_fault_record`，先转成 `{"tool": ..., "times": ...}` 再交给 `TraceRecorder`。该修正随 `14c20b2 feat: add cli, markdown output and offline mock entry` 提交，并由 `tests/test_cli.py::test_fault_plan_is_serialized_into_trace` 固定。

### 8. Web 工作台实现中的问题

- **开发环境禁止本机回环连接。** `asyncio` 在 Windows 上建事件循环依赖回环 socket，所以 FastAPI、uvicorn 和 `TestClient` 一启动就卡死。发现方式：用 `faulthandler` 打印卡住时的调用栈，停在 `socket.socketpair` 的 `accept`。处理：后端改用标准库 `ThreadingHTTPServer`，路由集中到不依赖 socket 的 `dispatch()`。

### 10. 用界面实际跑，跑出两个 UI 缺陷

**问题一：`needs_input` 只显示一句话，没有任何补救入口。**

### 11. 分镜序号为 0 或负数能通过全部检查

**问题。** `ShotDraft.id` 只是 `int`，`check_rules` 原本只查重复、不查正负。于是分镜序号填 `0` 或 `-1` 的脚本能通过时长和规则两项检查并提交，`script.md` 的表格里会出现“-1”这样的序号——那是给人看的定位，负号没有意义。

**发现方式。** 交付前手工探测边界值时发现：构造 `id=0` 和 `id=-1` 的两份草稿，`check_rules` 都返回 `pass`、零违规。

**修复。** 按项目一直在用的 TDD 流程走：先写 `tests/test_rules.py::test_non_positive_shot_ids_are_rejected`（对 `0` 和 `-1` 参数化），跑出 `2 failed`、报 `AssertionError: assert 'INVALID_SHOT_ID' in set()`，确认测试在旧实现上真的失败（RED）；再在 `check_rules` 里加序号校验，报 `INVALID_SHOT_ID`（GREEN）。全量从 317 涨到 319 passed，原有断言无回归。

**为什么值得单独记。** 这是本项目里唯一一次完整的 RED→GREEN 由本人完成，也是第 3 条“以 TDD 推进”的直接证据——`git show` 能看到测试和实现落在同一个提交里，而测试在加实现之前是红的。

## 最难问题

**最难的不是把功能做出来，是判断“状态全绿到底算不算做对了”。**

前两批真实运行 10/10 达到预期状态，316 条测试全过，一致性测试逐镜核对时长和引用原文——所有信号都指向“可以交了”。但把 5 个 `completed` 的脚本逐句读下来，发现“字幕放哪都行”“它能帮你搞定”这类句子根本不在 P01 的“支持字幕”里。规则没拦，测试也测不出来。

真正的难点在于意识到**测试只能证明“符合规则”，证明不了“规则够用”**。当时的测试断言的是 `check_rules` 返回 `pass`，而被测对象本身有洞，测试就跟着一起漏——这不是测试写得少，是判据选错了。

换判据之后问题变得可解：不再问“`check_rules` 过没过”，改问“这句旁白能不能对应到某条 `facts` 原文”。拿这个标准重审，5 个脚本全不达标。于是收紧 Prompt、把词表从 24 个扩到 62 个、把问题句子写成回归测试，再全量重跑第三批。

第二个难点是**改了规则之后旧记录全部失效**。新词表下旧的 5 个 `completed` 样例全部不再通过，`test_completed_results_recompute_exactly` 直接失败。第一反应是“只重跑失败的几个”，但那样 `examples/real/` 就成了两批不同规则的混合物，一致性测试失去意义。最后决定 10 个全部重跑——多花一倍时间，换记录自洽。

第三个是**架构约束比题目更严**。为了让娱乐向选题能跑通，加了一套 8 条素材的素材库，结果发现“纯剧情、零产品植入”被 `NO_SOURCE` 硬拦，永远无法 `completed`。题目只要求产品事实可追溯，并没有要求必须植入产品；用户实际要求“不带产品的搞笑短剧”时，模型追问“是否接受不出现产品”其实是在问一个代码不允许的选项。这个问题到交付也没改，因为它牵涉产品定义，不是纯技术决定。

## 学习收获

- **判据选错，测试越多越危险。** 316 条测试全绿，反而让人相信“做对了”。真正的问题不在覆盖率，在于断言的对象（“符合规则”）和想要的性质（“没有编造”）不是一回事。换判据之后同样的代码立刻暴露问题——这说明写测试之前先问“我在验证什么性质”比补测试重要。
- **能自动判定的约束，比写在提示词里的要求可靠得多。** `draft_hash` 只做一件事：提交的稿子必须是检查过的那一份。十几行代码，让“检查一份、提交另一份”这条路彻底走不通，比在 Prompt 里反复叮嘱管用。同理，把时长从模型口述改成工具返回，审核时就不需要判断哪句话是谁说的。
- **不要替模型做“该怎么改”的决定。** 代码里没有“超时长就截断”“失败就重试”这类分支，只有上限、协议和判定。效果是 Trace 里能看到模型真的在读违规清单改稿（`01_normal` 第 5 步一次报出三类违规、第 7 步又拦下“上手”），而不是模型心算后一次写对。代价是回合数变多。
- **文档里的数字要能重算，否则就是债。** 交付前复核时发现文档记的 `316 passed` 与实跑不符——不是有人记错，是环境变了（回环从不可用变为可用），而文档没人重跑。数字一旦写死就会腐坏，得有一条“怎么重算”的路径。
- **限制要写到能被复现，而不是只承认存在。** 九条已知限制每条都给了触发方法（引用 P01 写“说过的话都会出现在屏幕上”能过检查、`第一次` 会被 `第一` 误拦）。评审真正会问的是“你知道它错在哪吗”，而不是“它有没有错”。

## 下一步

按优先级：

1. **决定“纯剧情”要不要支持。** 现在 `check_rules` 第一条就是必须至少引用一条素材，所以“不带产品的搞笑短剧”只能追问或硬插两句广告词。两个方向：保留，就把“本项目只做产品推广脚本”写进 `docs/01-requirements.md` 的范围外，并在 system prompt 里明确告诉模型不要给出纯剧情这个选项；降级成风险提示，纯剧情就能生成，结果里如实标注“未引用任何产品素材”。我倾向前者——从实际跑出来的脚本看，硬插的那两句产品台词反而更难读。
2. **修 `needs_input` 的界面出口。** 缺素材时界面只显示“去改 data/materials.json”，而素材库是服务端白名单，前端改不了；`editor.js:161` 又把 `materials` 从可聚焦字段里过滤掉，导致“去补充”只能把焦点送到主题框，补完再点“生成”还会新开一次运行。应该改成：缺素材时直接给素材库下拉框，选完就地重跑。
3. **扩素材库。** 默认库 6 条素材、7 条事实，全部用上也只到 19.5 秒，撑不起 30 秒有信息量的脚本，模型只能靠重复或情绪铺垫凑时长。一个卖点至少要有三到五条事实。
4. **补语义层面的校验。** 现在词表是子串匹配，换说法就漏。可行方向是加一次独立的事实审校（另一次模型调用或人工抽检），但要先算清“判定不可复现”和“成本翻倍”这两个代价。
5. **让被跳过的测试不再静默。** `test_real_socket_roundtrip` 带 `skipif` 探针，环境不允许回环时会静默跳过，只看 `0 failed` 会误以为覆盖了。应该在验收脚本里显式检查这条是否真的执行过。
